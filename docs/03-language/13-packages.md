# 13. Пакеты, области видимости и bind

Пакет объединяет определения, которые должны быть одинаковыми в нескольких
модулях: тип команды, перечисление состояний протокола, константы и чистые функции.
Пакет не является экземпляром аппаратного блока и не имеет портов.

## Определение и импорт

```systemverilog
package bus_pkg;
  parameter int ADDR_W = 12;
  typedef logic [ADDR_W-1:0] address_t;
  typedef struct packed {
    address_t address;
    logic write;
  } request_t;
endpackage

module request_register (
  input logic clk,
  input bus_pkg::request_t request_in,
  output bus_pkg::request_t request_out
);
  always_ff @(posedge clk) request_out <= request_in;
endmodule
```

`bus_pkg::request_t` — явное квалифицированное имя. `import bus_pkg::request_t;`
делает доступным отдельное имя, `import bus_pkg::*;` — допускает поиск имён
пакета при обращениях. Wildcard import не означает текстовую вставку всего пакета.
Если два пакета предоставляют одинаковое имя, разрешайте неоднозначность явно.

Объявление типа в пакете должно быть скомпилировано до использования. Если имя
нужно в заголовке модуля, импорт внутри тела уже слишком поздний для такого
обращения; используйте квалифицированное имя или допустимый импорт в заголовке.
Пакет можно реэкспортировать через `export`, но не стоит скрывать происхождение
критичных интерфейсных типов за длинной цепочкой wildcard-импортов.

## Области и единицы компиляции

Есть области пакетов, модулей, интерфейсов, классов, подпрограмм и именованных
блоков. Внутреннее объявление может затенить внешнее. Иерархический путь
обращается к конкретному экземпляру, `::` — к содержимому типа/пакета и другим
областям, где разрешён этот оператор. Точка также выбирает поле структуры
или член объекта; одинаковый знак не делает эти обращения эквивалентными.

`$unit` обозначает область единицы компиляции. Какие файлы составляют одну
единицу, зависит от запуска компилятора. Общая переменная на уровне файла
может неожиданно исчезнуть из видимости при изменении файлового списка.
Для переносимых общих определений используйте пакеты. `$root` относится
к корню иерархии, а не к области пакета.

Восходящий поиск иерархических имён и ссылки на внутренние сигналы допустимы
в некоторых контекстах, но делают компонент зависимым от места включения.
Пакет не должен подменять интерфейс модуля обращениями к случайному `top`.
Встроенный пакет `std` предоставляет, например, `process`, `mailbox`,
`semaphore` и средства рандомизации.

## bind и checker

`bind` добавляет проверяющий модуль/интерфейс/checker в существующий контекст
без редактирования исходного RTL. Это удобно, когда одна и та же проверка
нужна для всех экземпляров блока.

```systemverilog
// Фрагмент проекта проверки: DUT называется request_register.
module register_check(input logic clk, input bus_pkg::request_t request_in);
  assert property (@(posedge clk) !$isunknown(request_in));
endmodule

bind request_register register_check u_check(.clk(clk), .request_in(request_in));
```

Имена в подключениях разрешаются относительно целевого контекста. Привязка
к типу модуля и привязка к конкретному экземпляру дают разный охват.
`checker` предоставляет специализированный контейнер проверок с собственными
правилами аргументов и событий; это не обычный синтезируемый модуль хранения.
Семантика `assert property` подробно вводится в
[главе 27](../05-verification/27-assertions.md).

## Практика организации

Храните интерфейсные типы в небольших пакетах без глобального изменяемого
состояния. Для проектов полезен явный файловый список: пакеты, интерфейсы,
RTL, затем тестбенч. Не включайте один и тот же файл пакета через `include`
во множество модулей: это создаёт повторные определения и зависимость от guards.
Условная компиляция пакета должна иметь одинаковый смысл во всех зависимых файлах.
