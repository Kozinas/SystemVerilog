# 15. Интерфейсы и modport

Интерфейс объединяет связанные сигналы в именованный объект и может описывать
допустимые роли участников. Вместо независимых портов `valid`, `ready`, `data`
модуль получает один интерфейс потока. Это уменьшает вероятность перепутать
каналы, но само по себе не проверяет временной протокол.

## Объявление и роли

```systemverilog
interface stream_if #(parameter int W = 8) (input logic clk);
  logic valid, ready;
  logic [W-1:0] data;
  modport source (input clk, ready, output valid, data);
  modport sink   (input clk, valid, data, output ready);
endinterface

module stream_wire(stream_if.sink input_bus, stream_if.source output_bus);
  assign output_bus.valid = input_bus.valid;
  assign output_bus.data = input_bus.data;
  assign input_bus.ready = output_bus.ready;
endmodule
```

Направления modport читаются **со стороны подключённого модуля**. Источник
выдаёт `valid/data` и принимает `ready`. Приёмник делает обратное. Modport
не создаёт отдельную копию сигналов и не является механизмом аппаратной защиты.
Он задаёт допустимый доступ через соответствующий вид интерфейса.

## Экземпляры и соединения

В верхнем модуле создают `stream_if #(.W(8)) bus(clk);`, затем передают `bus`
в интерфейсный порт экземпляра. Можно указать роль в объявлении порта модуля
или выбрать разрешённый modport при подключении. Согласуйте эти способы,
чтобы не получить конфликтующие объявления ролей.

Типизированный порт `stream_if.sink p` фиксирует семейство интерфейса.
Generic-форма с ключевым словом `interface` оставляет конкретный интерфейс
для соединения; она полезна обобщённым блокам, но уменьшает очевидность контракта.
Параметры экземпляра интерфейса должны давать согласованные ширины для обеих сторон.

Интерфейсы могут передаваться другим интерфейсам; возможны массивы экземпляров.
Объявления на уровне проекта удобнее локально вложенных вариантов для совместного
использования. `.name` и `.*` сохраняют общую идею неявных соединений, однако
совместимость интерфейсов и modport проверяется по отдельным правилам.

## Методы и внутренние процессы

Интерфейс может содержать функции, задачи, непрерывные присваивания и процессы.
`import` в modport предоставляет доступ к методу интерфейса; `export` участвует
в схемах, где реализацию метода предоставляет подключённая сторона. Это
не тот же `import`, что импорт пакета, и не DPI-import.

Хранить счётчик протокола внутри интерфейса допустимо, но нужно понимать, кто
им владеет и сколько экземпляров создаётся. Не переносите в общий интерфейс
скрытые драйверы сигналов, которые уже записывает модуль-источник.
Многие синтезаторы поддерживают только определённое подмножество интерфейсных
возможностей; наличие задачи с `@` меняет характер интерфейса на проверяющий.

## Clocking и virtual interface

Clocking block задаёт момент наблюдения и подачи сигналов тестбенча относительно
события такта. Он имеет собственные направления и skew; это отличается
от modport, который в первую очередь описывает доступ. Подробнее —
[глава 23](../05-verification/23-testbenches.md).

Класс не создаёт аппаратный экземпляр интерфейса. `virtual interface` хранит
ссылку на уже существующий интерфейс, чтобы драйвер или монитор класса мог
работать с сигналами. До доступа такую ссылку нужно присвоить; `null` не является
интерфейсом. Параметры и выбранный modport участвуют в совместимости virtual-типа.

Для переносимого RTL начинайте с простого интерфейса данных и modport.
Временные задачи, clocking, проверки и virtual handles добавляйте в слой проверки
с ясным разделением владельцев сигналов.
