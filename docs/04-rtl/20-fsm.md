# 20. Конечные автоматы и протоколы

Конечный автомат хранит ограниченное состояние и выбирает переход по входам.
Он удобен, когда действие требует нескольких тактов: ожидание запроса,
запуск операции, ожидание завершения, выдача ответа.

## Moore и Mealy

У автомата Moore выход зависит от состояния, у Mealy — также от текущих входов.
Mealy может реагировать без дополнительного такта, но создаёт комбинационные
пути через границу блока. Если несколько блоков зависят друг от друга
комбинационно, легко получить длинный путь или петлю.

Полный небольшой автомат с однотактовым выходом done:

```systemverilog
module controller (
  input logic clk, rst_n, start, finished,
  output logic busy, done
);
  typedef enum logic [1:0] {IDLE, RUN, REPORT} state_t;
  state_t state, next_state;

  always_comb begin
    next_state = state;
    busy = 1'b0;
    done = 1'b0;
    case (state)
      IDLE:   if (start) next_state = RUN;
      RUN: begin
        busy = 1'b1;
        if (finished) next_state = REPORT;
      end
      REPORT: begin
        done = 1'b1;
        next_state = IDLE;
      end
      default: next_state = IDLE;
    endcase
  end

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) state <= IDLE;
    else        state <= next_state;
endmodule
```

`done` активен один полный интервал состояния REPORT. Если `start` остаётся
высоким до возвращения в IDLE, автомат примет новый запуск. Если это не нужно,
протокол должен требовать импульс, handshake или ожидание снятия start.

## Разделение состояния и вычисления

Два процесса отделяют регистр состояния от функции перехода. Однопроцессный
стиль тоже корректен, если временная семантика ясна. Главный критерий — понятность
момента принятия входа, обновления регистров и доступности выхода.

`next_state = state` описывает сохранение текущего состояния по умолчанию.
Выходы получают отдельные безопасные значения, чтобы избежать защёлок.
Регистр данных может обновляться в самостоятельном `always_ff`, но каждый
регистр должен иметь одного владельца.

## Кодирование и ошибочные состояния

Binary-кодирование экономит триггеры, one-hot может упростить переходы.
Синтезатор способен перекодировать FSM согласно своим настройкам. Явно заданный
код состояния не всегда сохраняется физически без дополнительных ограничений.
Не подключайте внешние потребители к внутреннему коду состояния без контракта.

`default: next_state = IDLE` задаёт поведение модели для неописанного кода.
Но безопасность при аппаратном сбое зависит от сохранения такой логики
синтезом и от выбранной архитектуры, а не только от наличия default.
Assertion допустимых состояний обнаруживает ошибку; она не восстанавливает схему.

## Протоколы и liveness

Safety-свойство говорит «плохое никогда не происходит», например done и busy
не активны одновременно. Liveness говорит «хорошее когда-нибудь происходит»,
например любой принятый запрос завершается. Для второго нужны допущения:
если `finished` никогда не приходит, автомат не обязан сам завершить работу.

Тестируйте переходы, повторный запрос, сброс посреди RUN, длительные ожидания
и неожиданные комбинации входов. Покрытие всех состояний не гарантирует
покрытия всех переходов и последовательностей протокола.
