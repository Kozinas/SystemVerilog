# 24. Параллельные процессы и синхронизация

Модульные `initial`/`always` уже работают параллельно. `fork` позволяет создать
дочерние процессы внутри процедуры. Родитель и дети разделяют доступные объекты,
поэтому время жизни данных и способ передачи результата нужно определить явно.

## join, join_any, join_none

`fork ... join` ждёт все дочерние процессы. `join_any` ждёт первый завершившийся,
остальные продолжают работу. `join_none` сразу позволяет родителю двигаться дальше;
порождённые процессы начинают исполнение, когда родитель приостановится или завершится.

```systemverilog
// Фрагмент задачи тестбенча, изолирующая область для тайм-аута.
fork
  begin
    fork
      begin wait (done); end
      begin #1us; $fatal(1, "Operation timeout"); end
    join_any
    disable fork;
  end
join
```

Изолирующий внешний процесс ограничивает набор детей, которые попадут под
`disable fork`. В произвольном большом driver такой оператор иначе может
остановить не только таймер, но и другие дочерние работы текущего процесса.
После `join_any` оставшаяся ветвь не исчезает автоматически.

`wait fork` ждёт дочерние процессы вызывающего процесса. `disable name`
останавливает именованный блок/задачу по правилам языка; при повторных
параллельных активациях это может иметь более широкий эффект, чем ожидается.

## Захват переменных цикла

```systemverilog
// Фрагмент тестбенча.
for (int i = 0; i < 4; i++) begin
  automatic int id = i;
  fork
    $display("worker %0d", id);
  join_none
end
wait fork;
```

Отдельный `automatic id` сохраняет индекс данной итерации до запуска ребёнка.
Если все дети читают одну изменяемую `i` после окончания цикла, они могут
увидеть конечное значение. Область объявления и момент инициализации
существеннее слова `automatic`, добавленного в случайное место.

## Events и ожидание

`event e;` создаёт объект события. `-> e` немедленно запускает ожидающих
на событии, `->> e` использует неблокирующее планирование. `@e` ждёт будущее
срабатывание и может пропустить уже случившееся в том же временном слоте.
`wait(e.triggered)` использует признак срабатывания, сохраняющийся в течение
слота, и помогает избежать этой конкретной гонки.

`wait(expr)` проверяет уровень условия и ждёт его истинности. `@(posedge x)`
ждёт событие перехода. `wait_order(e1,e2)` проверяет порядок именованных событий
с действиями успеха/ошибки. Ни один из этих операторов не создаёт автоматически
очередь исторических событий: для передачи нескольких объектов нужна коллекция.

## Mailbox, semaphore, process

Типизированный `mailbox #(transaction_t)` передаёт транзакции между процессами.
`put/get/peek` могут блокироваться, `try_put/try_get/try_peek` возвращают
результат попытки. Ограниченная mailbox позволяет моделировать backpressure.
Если передаётся handle класса, отправитель и получатель видят один объект,
пока не сделана явная копия.

`semaphore` управляет ключами доступа: `get(N)` ждёт N ключей, `put(N)` возвращает,
`try_get(N)` пробует без ожидания. Это не автоматическое обеспечение честности
любого пользовательского протокола; забытый возврат ключа создаёт зависание.

`process::self()` возвращает handle процесса. Через `status`, `suspend`,
`resume`, `kill`, `await` можно тонко управлять выполнением. Остановка процесса
не является универсальным механизмом освобождения всех приобретённых им
ресурсов; завершение работы должно быть частью архитектуры теста.
