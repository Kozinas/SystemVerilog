# 33. Стандарты, изменения 2023 и рабочий процесс

Редакция языка, режим компилятора и синтезируемое подмножество — три разные
характеристики проекта. Для новых конструкций нужна явная проверка версии,
а для аппаратного проекта ещё и подтверждение синтеза нужной структуры.

## Нормативная база после 2022 года

По карточке IEEE, **IEEE 1800-2023** активен, утверждён 6 декабря 2023 года
и опубликован 28 февраля 2024 года. Он заменяет 1800-2017; PDF доступен через
IEEE GET при поддержке Accellera. Проверка источника выполнена 23 сентября
2026 года. Более позднюю редакцию эта методичка не предполагает.
[Карточка стандарта](https://standards.ieee.org/ieee/1800/7743/).

Обновление содержит дополнения, исправления и уточнения. Не следует приписывать
2023 году давно существовавшие `always_ff`, интерфейсы, классы или assertions.
Они используются в основном тексте как устоявшиеся средства языка.

## Карта изменений

Для выбора тем сверены первичные release notes реализации slang
[v6.0](https://github.com/MikePopoloski/slang/releases/tag/v6.0) и
[v7.0](https://github.com/MikePopoloski/slang/releases/tag/v7.0).
Это сведения реализации об обновлении языка; при споре нормативным источником
остаётся IEEE 1800-2023, а не принятый одним инструментом текст.

| Область | Что появилось/расширено | Практический смысл |
| --- | --- | --- |
| Строки | Многострочные литералы с тройными кавычками | Удобнее длинный текст моделей |
| Препроцессор | Логические условия в условных директивах | Меньше вложенных условий |
| Типы | Soft packed unions, ограничения типовых параметров | Более гибкие представления |
| Подпрограммы | `ref static` | Явное требование lifetime аргумента |
| Массивы | `map`, расширения итераторов | Преобразование коллекций |
| Классы | Ограничения наследования/переопределения, weak references | Более строгие объектные контракты |
| Coverage | Средства управления автоматически остающимися cross bins | Точнее цель покрытия |

Примеры новых конструкций в [sv2023.sv](../../examples/language/sv2023.sv)
проверяются отдельно в режиме 1800-2023. Остальные примеры ориентированы
на обычный синтаксис 2017, чтобы основной курс не зависел от новых расширений.
Это выбранная политика переносимости, а не обещание поддержки любым EDA.

## Пример новых типов и строк

```systemverilog
// Объявления для режима SystemVerilog-2023.
typedef union soft packed {
  logic [31:0] wide;
  logic [7:0] narrow;
} overlay_t;
string help_text = """First line
Second line""";
```

Размер объединения определяется наибольшим членом. Разноразмерные представления
перекрываются по правилам soft union; операции через узкий член требуют внимания
к старшим битам. Не используйте это как неявный протокол упаковки без теста
ожидаемого расположения данных. Строка нужна тестбенчу, а не аппаратной памяти
фиксированного формата.

## Инструменты и уровни проверки

Slang выполняет разбор, семантическую проверку и элаборацию, но не моделирует
время выполнения. В репозитории используется pyslang, Python-интерфейс этого
компилятора. Это позволяет проверить пакеты, классы, SVA и примеры новой редакции
без утверждения, что они были симулированы.
[Документация slang](https://www.sv-lang.com/user-manual.html).

Icarus Verilog удобен для небольших переносимых примеров; набор SV-возможностей
нужно проверять по выбранной версии. Verilator поддерживает свой набор
языковых возможностей и режимов моделирования; детали X/Z, coverage,
assertions и timing необходимо читать для конкретной версии.
[Документация Verilator](https://verilator.org/guide/latest/languages.html).

Yosys и коммерческие FPGA/ASIC-синтезаторы имеют разные frontends и ограничения.
Вывод RAM, интерфейсов и начальных значений проверяйте по документации производителя
и отчёту синтеза. Смена расширения файла с `.v` на `.sv` не подтверждает полную
поддержку 1800-2023.

## Практический цикл

1. Записать интерфейс, допустимые параметры, события принятия и задержку.
2. Выполнить lint/компиляцию и элаборацию граничных конфигураций.
3. Запустить направленные тесты, затем случайные с сохранёнными seed.
4. Проверить assertions и покрытие, разобрать все предупреждения по смыслу.
5. Выполнить синтез, посмотреть ресурсы/память/защёлки и timing/CDC/RDC.
6. Сохранить исходники, команды, версии и результаты в воспроизводимом flow.

Для этой методички [VALIDATION.md](../../VALIDATION.md) фиксирует только
действительно выполненные проверки. Текстовые фрагменты объясняют локальную
конструкцию; самостоятельные файлы examples служат базой исполняемых проверок.
